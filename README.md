# Building-A-Semantic-Vector-Database-
You are coming in as a Data Infrastructure Engineer for the AI Search Initiative. Your responsibility is architect, and deploy the end-to-end data pipeline required to ingest, transform, and manage the semantic data foundations . You are expected to deliver data-engineering solutions that will help build a scalable AI infrastructure on premise.

## Pipeline walkthrough and data-quality review

This review is based on [ingestion.py](./ingestion.py), [transformation.py](./transformation.py), and [load_gold.py](./load_gold.py). It describes what those scripts currently do and distinguishes that from recommendations; the proposed controls below are not implemented in the scripts.

### How the pipeline works

See [ARCHITECTURE.md](./ARCHITECTURE.md) for the diagram and full code-verified column lineage. The dependencies between the scripts' input and output paths imply this execution order; no scheduler or orchestrator is shown:

1. **Ingest and join (`ingestion.py`)**: reads gzipped JSONL metadata from `data/bronze/metadata/*.jsonl.gz` and review records from `data/bronze/review/*.jsonl.gz` (lines 12–43). It selects product metadata (`parent_asin`, `title`, `main_category`, `price`) and review fields (`parent_asin`, `user_id`, `rating`, `text`, `timestamp`); replaces missing prices with `0.0`; removes duplicate metadata rows by metadata product key; drops reviews whose text is null; and inner-joins reviews to metadata on product key. The result is written with overwrite mode to `data/silver/complete_reviews` (lines 9–10, 45).
2. **Build gold tables (`transformation.py`)**: reads the silver Parquet dataset (lines 13–18). It creates `dim_products` from product metadata, `dim_users` with review count and average rating, and `fact_vectors` by splitting review text into overlapping chunks of up to 60 words with 10 words of overlap (lines 45–72, 74–101). These are written as Parquet to `data/gold/dim_products`, `data/gold/dim_users`, and `data/gold/fact_vectors`.
3. **Create embeddings (`load_gold.py`)**: reads `data/gold/fact_vectors`, instantiates the `all-MiniLM-L6-v2` SentenceTransformer model, computes one embedding for each `review_chunk`, and writes the rows plus an `embedding` array to `data/gold/final_vector_storage` (lines 15–32).

All paths are relative to the process working directory. Each script configures Spark to use `local[*]`; that means execution is local to one machine, not a distributed production cluster.

### Sources, tasks, and destinations

| Stage | Source | Main task | Destination |
|---|---|---|---|
| Ingestion | Gzipped JSONL product metadata and review files under `data/bronze/` | Select fields, deduplicate metadata, filter null review text, inner join | `data/silver/complete_reviews` (Parquet) |
| Gold transformation | `data/silver/complete_reviews` (Parquet) | Build product and user dimensions; split review text into overlapping chunks | `data/gold/dim_products`, `data/gold/dim_users`, `data/gold/fact_vectors` (Parquet) |
| Embedding | `data/gold/fact_vectors` (Parquet) and the `all-MiniLM-L6-v2` model | Encode each chunk as a vector | `data/gold/final_vector_storage` (Parquet) |

The code shown does **not** connect to a relational database, a vector database, or a search/indexing service. Despite the `load_gold.py` name and the “Database Loading” message in `transformation.py:104`, the final sink is a local Parquet directory. The current workspace data listing contains silver and gold output folders, but no files under the expected bronze input paths, so raw-input counts and an end-to-end rerun could not be verified from the available data.

### Findings, impact, and suggested solutions

The production cost descriptions below are risk assessments based on the code shape, not measured runtime or cloud-billing results. Actual cost depends on input size, cluster/runtime, storage, and model throughput.

| File and lines | Finding | Technical impact | Plain-language impact | Suggested solution |
|---|---|---|---|---|
| `ingestion.py:21–23` | Missing price is replaced with `0.0`; metadata deduplication picks one row per product key without an explicit ordering rule. | Unknown price becomes indistinguishable from a real zero price. Duplicate-key selection may not be repeatable, and conflicting metadata is not reconciled. | A missing price can look like a free product, and reruns may retain different product details. | Preserve null or add a separate missing-price indicator. Define a deterministic “current/best” metadata rule and measure duplicate/conflict rates before deduplicating. |
| `ingestion.py:28–35` | Review quality filtering only excludes null text. | Empty/whitespace text, null or malformed identifiers, invalid ratings, and invalid timestamps can pass; schema/type assumptions are not checked here. | Blank reviews or impossible ratings can contaminate the data and user averages. | Define a source schema and required-field, trim/non-empty, rating-range, timestamp, and identifier checks. Quarantine rejected rows with reason codes and counts. |
| `ingestion.py:39–45` | Inner join excludes every review without matching metadata; the output is overwritten. | Unmatched reviews are silently lost. Full overwrite makes each run a full rebuild and can replace the prior good output if a run fails during publication. | Reviews disappear when metadata is late or missing, and a failed refresh can disrupt consumers. | Reconcile input, matched, and unmatched counts; send unmatched records to a quarantine/late-arrival path. Publish validated output atomically/versioned, then promote it; make reruns idempotent. |
| `ingestion.py:14,26` | JSON inputs are read directly from wildcard paths without visible schema enforcement or file-level audit. | Schema inference and repeated full scans can add work; unexpected schema changes can alter types/columns. No manifest establishes exactly which source files were processed. | New or malformed source files can change results unexpectedly, and it is hard to trace a bad record back to its input. | Supply an explicit/validated schema, record input file names and batch identifiers, and alert on schema drift or unreadable files. |
| `ingestion.py:23,35,47`; `transformation.py:80,89,102` | Counts are actions separate from writes, and several frames are evaluated again when written or counted. No cache/persist is used. | Spark actions trigger jobs and scans; the count after the silver write can recompute the join, and the final fact count can recompute chunking. This adds CPU, I/O, and elapsed time. | The same work may be done more than once just to print progress. | Use a single planned metrics/reconciliation pass, persist only when reuse justifies its storage cost, or write then obtain counts from controlled output metrics. Avoid a post-write full recomputation solely for logging. |
| `ingestion.py:45`; `transformation.py:81,90,101` | Silver and the three gold datasets use `coalesce(1)` and overwrite their destinations. | `ingestion.py:6`; `transformation.py:7–11`; `load_gold.py:8–13` | Spark runs with `local[*]` and hardcoded 20 shuffle partitions / 4 GB memory settings. | The pipeline is constrained to one host and fixed resource assumptions; local-mode executor settings do not create scalable cluster capacity. Empty chunk arrays also disappear during explode. | Longer reviews cost extra to encode, while short or unchunkable ones may not appear in search. | Measure chunk counts and retrieval quality; select limits/overlap based on evaluation. Consider sentence-aware boundaries, and reconcile source reviews with zero chunks. |
| `transformation.py:76–81` | `dim_products` uses `distinct()` over all selected fields, not one row per `product_id`. | Conflicting metadata for a product can produce multiple dimension rows despite the “unique products” log. | One product may appear more than once in the product table. | Enforce one row per product key using the deterministic metadata rule and test key uniqueness before publishing. |
| `transformation.py:85–90,94–100` | User aggregates and fact rows do not validate null keys/rating ranges; `timestamp` is discarded from the gold fact output. | Null `user_id` can form an aggregate group; invalid ratings affect averages. | `load_gold.py:19,21–25,32` | The model reference is unpinned, empty text returns an empty vector, and there are no output checks. | Model/version drift may change vectors; empty arrays can violate downstream expectations; dimension, null, NaN/Inf, and row-count correctness are not checked. | A later run may create incompatible vectors or apparently succeed while saving unusable embeddings. | Pin and record model revision and embedding configuration. Gate publication on non-null vector count, expected dimension (384 for the named model as used here), finite values, and input/output row reconciliation. |

#### Clarifying metadata deduplication

At `ingestion.py:17–22`, the code selects `parent_asin`, metadata fields, and then calls `drop_duplicates(["metadata_parent_asin"])`. Neither “keep the first row” nor `drop_duplicates` alone defines which duplicate should win: Spark DataFrames have no inherent row order, so “first” is meaningful only after an explicit ordering.

The recommendation to define a deterministic “current/best” rule is the **business decision** (for example, prefer the newest valid record, then a trusted source, then a stable tie-breaker). Explicitly keeping the first row after sorting by those fields is a possible **implementation** of that policy. They are not competing solutions: the policy determines what “best” means, and a deterministic ordering implements it. Measuring duplicate and conflicting-field rates first shows how often the choice matters and helps validate the rule; it does not replace the rule. If the source has no update time or trust indicator, a stable key-based tie-breaker can make the result repeatable, but it cannot establish which metadata is more correct.

### Proposed data-quality plan

These are recommendations for a pipeline quality plan; the scripts currently show no formal tests, quarantine, data contracts, or quality gates.

1. **Define contracts at each boundary.** Record expected schema and types for bronze metadata/reviews, silver joined reviews, gold dimensions/facts, and embedding output. Version the contract and treat unexpected required-field/type changes as a failed batch rather than silently adapting.
2. **Profile and validate bronze inputs.** Capture file names, sizes, row counts, parse failures, schema, and batch timestamp. Check required product/review keys, non-empty trimmed review text, rating range (confirm the source contract before choosing allowed values), valid timestamps, and price validity. Track null/duplicate rates and metadata key conflicts.
3. **Reconcile ingestion explicitly.** For every batch compare raw review rows to parsed, valid, rejected, matched, and unmatched rows. Do the same for metadata. Require the counts to balance; quarantine rejected/unmatched rows with reason and source file rather than dropping them silently.
4. **Validate silver before publication.** Check `parent_asin` and required review fields, expected join cardinality, duplicate policy, plausible values, and freshness. Compare the joined count against accepted matched reviews. Publish only after checks pass, preserving the last known-good version on failure.
5. **Gate gold dimensions and facts.** Require non-null/unique `product_id` in `dim_products`; validate `review_count` and `avg_rating_given`; verify each fact row has its source product/user/rating as required; check that every accepted review has a recorded chunk outcome. Monitor reviews-per-product/user and chunks-per-review for sudden shifts.
6. **Gate embeddings.** Require one output vector per eligible chunk, exactly the expected number of finite numeric elements, no null/empty vectors, and the configured model/revision. Reconcile embedding input and output counts and sample deterministic records for repeatability/drift.
7. **Use explicit severity and operations.** Fail and block promotion on schema/key/vector-contract breaks or materially unbalanced counts; warn/quarantine on agreed non-critical anomalies. Emit batch-level metrics and structured logs (including rejected counts and reasons), alert on failure, duration, row-count drift, and freshness, and make reprocessing idempotent.
8. **Test the quality rules.** Add small fixtures for duplicate/conflicting metadata, missing keys, blank/null text, unmatched products, invalid ratings/timestamps, short reviews, chunk overlap, empty chunk results, and invalid embedding dimensions/values. Include rerun/overwrite-failure tests and a representative-volume performance benchmark before production rollout.

**Uncertainty / verification limits:** No production cluster, source files, model-serving topology, measured dataset volume, or destination database is specified in these three scripts. Accordingly, numeric runtime/cost estimates, actual model-UDF serialization behavior, business-valid rating ranges, whether timestamps must be retained, and the intended downstream vector store remain unverified and should be confirmed with the pipeline owner and target environment.
