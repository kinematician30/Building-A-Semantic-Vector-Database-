# AeroMart Data Quality Checks Specification

## Purpose

This document defines proposed data-quality controls for the Silver and Gold/vector layers of the AeroMart semantic-search pipeline based on the findings in `docs/AUDIT_REPORT.md` and the verified behavior of the repository code. These checks are design controls only; they are not implemented in the pipeline scripts.

The checks below are derived from actual audit findings, not generic quality patterns. They distinguish integrity checks that should fail the pipeline from monitoring checks that should alert and track trends.

## Data Quality Checks Summary

The AeroMart data-quality design translates the production-readiness findings from the pipeline audit into measurable controls across the Silver, Gold, and final vector-storage layers.

The specification defines 10 core quality checks and 2 additional monitoring checks covering data completeness, semantic correctness, join retention, duplicate detection, key integrity, aggregate validity, chunk-generation survival, lineage, and embedding integrity.

### Silver Layer

- **DQC-01 — Required-Field Completeness:** Validates that structurally required Silver fields are populated while separately monitoring business-completeness fields whose acceptable null rates require an agreed baseline or SLA.
- **DQC-02 — Price Semantic Integrity:** Prevents unknown source prices from becoming indistinguishable from genuine zero prices. Missing-price state must be measured before transformation or preserved through an explicit flag.
- **DQC-03 — Bronze-to-Silver Join Retention:** Measures review retention and record loss caused by the metadata join. The loss rate is monitored until an acceptable business threshold is established.
- **DQC-04 — Duplicate Review Detection:** Detects exact and suspicious near-duplicate reviews that could distort aggregates, vector counts, and downstream search behavior.

### Gold Layer

- **DQC-05 — Product-Key Uniqueness:** Requires each `product_id` in `dim_products` to be unique.
- **DQC-06 — User Aggregate Validity:** Validates user uniqueness, positive review counts, and rating aggregates against the confirmed source-data rating contract.
- **DQC-07 — Chunk Integrity and Survival:** Hard-fails null or blank review chunks. Full review-to-chunk survival reconciliation requires stable source-review lineage before it can become an enforceable production control.
- **DQC-08 — Review/Chunk Lineage Integrity:** Defines stable `review_id` and `chunk_id` traceability as a required future production gate. The current repository does not yet provide these identifiers.

### Vector Layer

- **DQC-09 — Embedding Presence:** Requires every review chunk promoted to final vector storage to contain a non-null embedding.
- **DQC-10 — Embedding Dimensionality:** Requires every embedding generated by the current `all-MiniLM-L6-v2` model to conform to the expected 384-dimensional vector contract.

### Additional Monitoring

- **DQC-11 — Review Text Quality:** Monitors blank, whitespace-only, and short review text that may disappear during chunk generation.
- **DQC-12 — Review-to-Chunk Expansion:** Tracks the relationship between source-review volume and generated chunk volume to detect unexpected transformation drift or data loss.

Together, these controls establish three quality boundaries:

**Bronze → Silver:** protect source-data meaning and measure ingestion/join loss.

**Silver → Gold:** protect dimensional integrity, aggregation correctness, chunk quality, and lineage.

**Gold → Vector Storage:** protect embedding completeness and vector-schema integrity.

Checks with objective integrity requirements can operate as hard-fail gates. Checks requiring business tolerance—such as join-loss rate, duplicate rate, and chunk-expansion behavior—remain monitoring controls until representative baselines and explicit SLAs are established.

These controls are currently a production-readiness design specification. They are not implemented quality gates in the existing AeroMart pipeline.

## Scope and Evidence Basis

The proposed checks are grounded in the verified implementation:

- `ingestion.py:16-47` defines the Silver dataset and the Bronze-to-Silver join.
- `transformation.py:74-101` creates the Gold dimension and fact tables.
- `load_gold.py:15-33` creates the final vector dataset.

This specification intentionally follows the repository evidence and does not assume additional infrastructure beyond the current code path.

## Check Categories

- Hard-fail integrity checks: conditions that must hold before the pipeline is allowed to continue.
- Warning/monitoring checks: conditions that should raise an alert or trigger investigation but may not be treated as a full pipeline failure depending on the business SLA.

## Proposed Checks

### DQC-01 — Silver required-field completeness
- Pipeline layer: Silver
- Dataset: `data/silver/complete_reviews`
- Quality dimension: Structural completeness / required-field validity
- Audit finding/risk addressed: P0-03 Missing Silver/Gold/vector quality gates; P1-05 Inner-join record loss is not measured or validated
- Columns involved: `parent_asin`, `user_id`, `rating`, `text`, `timestamp` are the structurally required columns for the Silver record contract as implemented in `ingestion.py:28-34`; `title`, `main_category`, and `price` are retained metadata fields and should be treated as business-completeness fields unless a contract later defines them as mandatory.
- Validation rule: Structurally required Silver fields must be present and not null for records accepted into Silver. Business-completeness fields (`title`, `main_category`, `price`) should be monitored for null rate, but their hard-fail requirement is not established by repository code alone.
- Suggested PySpark validation logic or pseudocode:

```python
structural_required = ["parent_asin", "user_id", "rating", "text", "timestamp"]
for c in structural_required:
    null_count = silver_df.filter(F.col(c).isNull()).count()
    if null_count > 0:
        raise ValueError(f"Silver structural completeness failure: {c} has {null_count} nulls")

# Business-completeness check only; threshold TBD until a baseline/SLA is established
business_fields = ["title", "main_category", "price"]
for c in business_fields:
    null_rate = silver_df.filter(F.col(c).isNull()).count() / silver_df.count()
    # alert only unless a business policy later defines a hard fail threshold
    pass
```

- Failure threshold: Hard-fail for structurally required fields with nulls. Business-completeness fields use `TBD — requires baseline/SLA` because the repository does not establish a mandatory null threshold for metadata quality.
- Severity: High
- Action on failure: Hard fail the pipeline for structurally required nulls; record and alert on metadata-field null rates without blocking the run until a business threshold is defined.
- Why the check matters: The Silver layer is the canonical cleaned input to Gold. Structural nulls can break the join contract and downstream transformations, while metadata nulls should be governed by product data policy rather than assumed to be a fatal integrity breach.

### DQC-02 — Silver price validity and preservation of unknown-price semantics
- Pipeline layer: Silver
- Dataset: `data/silver/complete_reviews`
- Quality dimension: Domain validity / semantic correctness
- Audit finding/risk addressed: P1-06 NULL price converted to zero changes the meaning of missing value
- Columns involved: `price`
- Validation rule: Distinguish a genuine zero price from a source NULL before the dataset is coalesced. The repository currently uses `coalesce(col('price'), lit(0.0))` in `ingestion.py:17-22`, which means a source NULL and a real zero value become indistinguishable in the Silver output. The quality control therefore must measure or preserve missing-price semantics before the fill occurs; post-transform Silver NULL counts cannot recover that information.
- Suggested PySpark validation logic or pseudocode:

```python
# Measure semantics before coalescing; do not rely on Silver NULL counts to recover the distinction
source_missing_price = bronze_df.filter(F.col("price").isNull()).count()
source_zero_price = bronze_df.filter(F.col("price") == 0.0).count()

# Recommended future preservation approach before fill
bronze_df = bronze_df.withColumn("price_missing_flag",
    F.when(F.col("price").isNull(), F.lit(True)).otherwise(F.lit(False)))

# After coalesce, Silver cannot distinguish true zero from source NULL without the preserved flag
```

- Failure threshold: Hard fail only if a downstream rule prohibits treating a missing price as zero. Missing-price rate remains `TBD — requires baseline/SLA` because the repository does not define a business threshold for acceptable missing-price frequency.
- Severity: High
- Action on failure: Block the pipeline if the downstream product catalog or pricing logic requires a preserved separation between unknown and zero; otherwise, alert and define an explicit `price_missing_flag` before any fill logic is applied.
- Why the check matters: Once `coalesce(price, 0.0)` has occurred, Silver alone cannot recover whether a price was originally null or genuinely 0.0, so analytics and downstream search/filtering can silently misclassify missing prices as valid zero-value offers.

### DQC-03 — Bronze-to-Silver inner-join retention / record-loss measurement
- Pipeline layer: Silver
- Dataset: `data/silver/complete_reviews`
- Quality dimension: Retention / join completeness
- Audit finding/risk addressed: P1-05 Inner-join record loss is not measured or validated; P0-03 Missing Silver/Gold/vector quality gates
- Columns involved: `review_clean.parent_asin`, `meta_clean.metadata_parent_asin`, `parent_asin`
- Validation rule: Measure how many reviews are retained after the Bronze-to-Silver join and report the join loss rate. This should be monitored separately from a total count so the pipeline can detect metadata sparsity or a bad join.
- Suggested PySpark validation logic or pseudocode:

```python
review_count_before_join = review_df.count()
meta_count_before_join = meta_df.count()
joined_count = silver_join.count()
loss_rate = (review_count_before_join - joined_count) / review_count_before_join if review_count_before_join else 0.0

if loss_rate > 0:
    # Log to monitoring; fail if above an agreed threshold
    pass
```

- Failure threshold: Warning by default unless an operational SLA is established; hard fail if loss exceeds `TBD — requires baseline/SLA` for the current dataset profile. The repository does not justify a specific numeric threshold.
- Severity: High
- Action on failure: Alert and quarantine the Silver output if loss exceeds the agreed threshold; include the drop counts in the run metadata.
- Why the check matters: The repo’s inner join can silently drop otherwise valid reviews if metadata is missing or mismatched. Without measurement, the pipeline can look successful while reducing the effective review corpus.

### DQC-04 — Silver duplicate-review detection
- Pipeline layer: Silver
- Dataset: `data/silver/complete_reviews`
- Quality dimension: Deduplication / duplicate detection
- Audit finding/risk addressed: P2-03 Metadata deduplication is non-deterministic; C-3 Only null text removed; review duplicates are not explicitly handled
- Columns involved: `user_id`, `parent_asin`, `rating`, `text`, `timestamp`
- Validation rule: Detect exact duplicate reviews and suspicious near-duplicate reviews that are likely repeated entries rather than genuine separate reviews.
- Suggested PySpark validation logic or pseudocode:

```python
# exact duplicate detection
exact_dup_count = silver_df.groupBy("user_id", "parent_asin", "rating", "text", "timestamp").count().filter("count > 1").count()
# near-duplicate detection on normalized text optional
normalized = silver_df.withColumn("text_norm", F.lower(F.regexp_replace(F.col("text"), r"\s+", " ").cast("string")))
near_dup_count = normalized.groupBy("user_id", "parent_asin", "text_norm").count().filter("count > 1").count()
```

- Failure threshold: Hard fail for exact duplicates when duplicates are known to be invalid; warning for near duplicates until business rules are defined. Exact threshold `TBD — requires baseline/SLA`.
- Severity: Medium
- Action on failure: Log duplicate counts, quarantine duplicates, and route them to a separate audit table for downstream review before writing final Silver.
- Why the check matters: Duplicate reviews can skew user averages, product sentiment, and vector counts. The current code does not define duplicate handling beyond null-text cleanup.

### DQC-05 — Gold product-key uniqueness
- Pipeline layer: Gold
- Dataset: `data/gold/dim_products`
- Quality dimension: Key integrity / uniqueness
- Audit finding/risk addressed: P0-03 Missing quality gates; A-5 Non-deterministic deduplication in metadata; C-10 No checks between layers
- Columns involved: `product_id`
- Validation rule: `product_id` must be unique in `dim_products`. The repository implements `.distinct()` on the product dimension but does not validate uniqueness against the expected key set (`transformation.py:76-81`).
- Suggested PySpark validation logic or pseudocode:

```python
product_key_dups = dim_products.groupBy("product_id").count().filter("count > 1")
product_key_dup_count = product_key_dups.count()
if product_key_dup_count > 0:
    raise ValueError(f"dim_products duplicate product_id count: {product_key_dup_count}")
```

- Failure threshold: Hard fail if any duplicate `product_id` exists. This is a primary key requirement for dimension integrity.
- Severity: High
- Action on failure: Stop pipeline and investigate the metadata deduplication rule before continuing to downstream fact generation.
- Why the check matters: Duplicate products can break downstream product-to-review relationships and create inconsistent product metadata.

### DQC-06 — Gold user aggregate validity
- Pipeline layer: Gold
- Dataset: `data/gold/dim_users`
- Quality dimension: Aggregate validity / referential integrity
- Audit finding/risk addressed: P0-03 Missing quality gates; C-10 No checks between layers
- Columns involved: `user_id`, `review_count`, `avg_rating_given`
- Validation rule: `user_id` must be unique, and `review_count` must be positive for retained users. The accepted range for `avg_rating_given` should be kept as a validation candidate only if the source review contract explicitly establishes a valid rating domain; the repository does not currently prove that the allowed range is 1-5 beyond the presence of a `rating` column in `ingestion.py:28-34`.
- Suggested PySpark validation logic or pseudocode:

```python
bad_review_count = dim_users.filter((F.col("review_count") <= 0) | F.col("review_count").isNull()).count()
user_dup = dim_users.groupBy("user_id").count().filter("count > 1").count()

# Rating-range validation is conditional on source-contract confirmation
rating_ok = True
if rating_ok:
    pass

if bad_review_count > 0 or user_dup > 0:
    raise ValueError("dim_users validation failed")
```

- Failure threshold: Hard fail if `user_id` is duplicated or if `review_count <= 0`. For `avg_rating_given`, use `TBD — requires source-contract confirmation` unless a requirement is explicitly established elsewhere in the repository or business contract.
- Severity: High
- Action on failure: Block pipeline and investigate the user aggregation stage before Gold is used for downstream analytic or search features.
- Why the check matters: Incorrect user aggregates can skew personalization and make review distribution analysis unreliable. The rating domain must be validated against a confirmed source contract instead of an inferred assumption.

### DQC-07 — Gold chunk completeness and chunk-generation survival
- Pipeline layer: Gold
- Dataset: `data/gold/fact_vectors`
- Quality dimension: Completeness / transformation survival
- Audit finding/risk addressed: P0-02 Silent chunking failure and data loss path; C-5 Reviews under 10 characters are dropped silently
- Columns involved: `product_id`, `user_id`, `rating`, `review_chunk`
- Validation rule: Each surviving review chunk must be non-empty after splitting. This should be treated as an immediate hard fail: a chunk row with a null or blank `review_chunk` is not valid input for embedding. The repository also permits silent data loss in the chunker (`transformation.py:45-47` and `:54-60`), but a source-review-to-chunk reconciliation back to the original review set remains limited until stable lineage IDs exist. The repository does not provide evidence that `(product_id, user_id, rating)` uniquely reconciles source reviews to generated chunks; therefore, that specific join-back check is not a current hard validation rule.
- Suggested PySpark validation logic or pseudocode:

```python
empty_chunk_count = fact_vectors.filter(
    F.col("review_chunk").isNull() |
    (F.trim(F.col("review_chunk")) == "")
).count()
if empty_chunk_count > 0:
    raise ValueError(f"fact_vectors empty chunks: {empty_chunk_count}")
```

- Failure threshold: Hard fail if any `review_chunk` is null or blank. Source-review-to-chunk survival reconciliation should be monitored only as `TBD — requires baseline/SLA` until stable `review_id` lineage exists.
- Severity: High
- Action on failure: Halt pipeline and investigate chunk generation or upstream text cleansing before embedding proceeds.
- Why the check matters: A null or blank chunk cannot be embedded and therefore cannot contribute to retrieval. The repository’s current chunking path can silently drop text, which reduces search coverage without an explicit alert.

### DQC-08 — Gold/vector lineage identifier completeness
- Pipeline layer: Gold / final vector storage
- Dataset: `data/gold/fact_vectors` and `data/gold/final_vector_storage`
- Quality dimension: Traceability / lineage completeness
- Audit finding/risk addressed: P1-03 Missing stable review/chunk lineage prevents traceability
- Columns involved: `product_id`, `user_id`, `rating`, `review_chunk`, `embedding` (future required lineage fields: `review_id`, `chunk_id`)
- Validation rule: This is a future required production gate and a current known design gap. The repository does not currently produce stable `review_id` or `chunk_id` identifiers, so the system cannot yet tie each vector row back to a source review and chunk in a reproducible way. This should be explicitly classified as a future production control, not a current repository compliance requirement.
- Suggested PySpark validation logic or pseudocode:

```python
required_lineage = ["review_id", "chunk_id"]
missing = [c for c in required_lineage if c not in final_vectors_df.columns]
if missing:
    raise ValueError(f"Missing required lineage fields: {missing}")
```

- Failure threshold: Hard fail once these lineage fields are implemented in production. At the present repository state, this is a required future control and a known design gap rather than a current code-compliance check.
- Severity: High
- Action on failure: Block index generation until each vector row can be traced to the originating review and chunk.
- Why the check matters: Without lineage, results cannot be audited, debugged, or explained to downstream product or business stakeholders.

### DQC-09 — Final embedding presence
- Pipeline layer: Final vector storage
- Dataset: `data/gold/final_vector_storage`
- Quality dimension: Completeness / vector field presence
- Audit finding/risk addressed: P0-03 Missing quality gates; P1-04 Embedding-dimension validation is absent; P0-02 Silent chunking failure/data loss path
- Columns involved: `embedding`, `review_chunk`
- Validation rule: Every chunk row must have an embedding present and non-null. The code calls `model.encode(text).tolist()` and writes the embedding; it does not validate presence before writing.
- Suggested PySpark validation logic or pseudocode:

```python
missing_embedding_count = final_vectors_df.filter(F.col("embedding").isNull()).count()
if missing_embedding_count > 0:
    raise ValueError(f"Final embedding missing count: {missing_embedding_count}")
```

- Failure threshold: Hard fail if any `embedding` is null. This is a basic integrity threshold.
- Severity: Critical
- Action on failure: Stop vector write and quarantine the batch for investigation before production indexing.
- Why the check matters: A null embedding means a source chunk cannot be used for similarity search; this is a direct retrieval failure.

### DQC-10 — Final embedding dimensionality check (expected 384)
- Pipeline layer: Final vector storage
- Dataset: `data/gold/final_vector_storage`
- Quality dimension: Schema validity / vector integrity
- Audit finding/risk addressed: P1-04 Embedding-dimension validation is absent; P0-03 Missing quality gates
- Columns involved: `embedding`
- Validation rule: Confirm every embedding has length 384 to match the current `all-MiniLM-L6-v2` model. The repository indicates that this model produces a 384-dimensional embedding, but the code does not enforce the dimension at runtime.
- Suggested PySpark validation logic or pseudocode:

```python
bad_dim = final_vectors_df.filter(F.size(F.col("embedding")) != 384).count()
if bad_dim > 0:
    raise ValueError(f"Embedding dimension validation failed: {bad_dim} rows invalid")
```

- Failure threshold: Hard fail if any embedding length is not 384. This is a strict model-contract validation and should be treated as critical.
- Severity: Critical
- Action on failure: Reject the batch and investigate model version, serialization, or vectorization changes before indexing.
- Why the check matters: Downstream similarity operations assume a fixed vector length; inconsistent dimensions can corrupt index creation and retrieval results.

## Additional Monitoring Checks (Recommended)

These are not core “hard fail” controls but are recommended because the repository shows operational risk without fixed numeric baselines.

### DQC-11 — Review text blank/whitespace and short-text rate
- Pipeline layer: Silver / Gold
- Dataset: `data/silver/complete_reviews` and `data/gold/fact_vectors`
- Quality dimension: Content validity / data completeness
- Audit finding/risk addressed: P0-02 Silent chunking failure and data loss path; C-3 Only null text removed; C-5 Short reviews silently dropped
- Columns involved: `text`, `review_chunk`
- Validation rule: Measure the rate of blank, whitespace-only, or short review text. The current code allows short text to be dropped silently and uses `if len(text) < 10: return []` (`transformation.py:47-49`).
- Suggested validation logic or pseudocode:

```python
blank_after_trim = silver_df.filter(F.trim(F.col("text")) == "").count()
short_text_count = silver_df.filter(F.length(F.trim(F.col("text"))) < 10).count()
```

- Failure threshold: Warning or alert; exact threshold `TBD — requires baseline/SLA`.
- Severity: Medium
- Action on failure: Trigger a monitoring alert and investigate whether short reviews are being lost intentionally or by a bug.
- Why the check matters: Hidden data loss in the review corpus reduces both customer trust and retrieval quality.

### DQC-12 — Gold review-to-chunk expansion ratio trend
- Pipeline layer: Gold
- Dataset: `data/gold/fact_vectors`
- Quality dimension: Transform completeness / ratio monitoring
- Audit finding/risk addressed: P0-02 Silent chunking failure and data loss; P2-01 repeated actions
- Columns involved: `product_id`, `user_id`, `review_chunk`
- Validation rule: Compare the count of source-review rows to the count of chunk rows to ensure the expansion ratio is within an expected range.
- Suggested validation logic or pseudocode:

```python
source_review_count = silver_df.count()
chunk_row_count = fact_vectors.count()
expansion_ratio = chunk_row_count / source_review_count if source_review_count else 0
```

- Failure threshold: Warning only until a stable baseline is established; threshold `TBD — requires baseline/SLA`.
- Severity: Medium
- Action on failure: Raise an alert and compare the increase with expected chunking behavior; do not fail the pipeline without a baseline.
- Why the check matters: A sudden drop in chunk count may mean data loss, chunker changes, or upstream quality drift.

## Hard-Fail vs. Warning Checks Summary

### Hard-fail integrity checks
- DQC-01: Silver required-field completeness
- DQC-02: Silver price semantic integrity (hard fail when downstream policy requires preservation of unknown-price state)
- DQC-03: Bronze-to-Silver join retention / record-loss measurement (if threshold reached)
- DQC-05: Gold product-key uniqueness
- DQC-06: Gold user aggregate validity
- DQC-07: Gold chunk completeness and chunk-generation survival
- DQC-08: Gold/vector lineage identifier completeness (once implemented)
- DQC-09: Final embedding presence
- DQC-10: Final embedding dimensionality = 384

### Warning / monitoring checks
- DQC-04: Silver duplicate-review detection (depending on business policy)
- DQC-11: Review text blank/short-text rate
- DQC-12: Review-to-chunk expansion ratio trend
- DQC-03: Bronze-to-Silver join retention when threshold is not yet established (monitor before hard fail)

## Operational Note

The repository is not currently implementing these checks; the purpose of this document is to define proposed AeroMart controls based on the completed audit. Before these checks become production policy, the team should measure real baseline behavior on representative data and define explicit business thresholds for record-loss tolerance, duplicate rates, and chunk expansion ratios.
